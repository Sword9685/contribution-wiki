欢迎来到贡献值模组 Wiki

贡献值模组（CSU-YSU 贡献值系统） 是面向 Minecraft Java Edition 26.3 的 Fabric 服务端模组，为生存服提供三套互相咬合的玩法：以 贡献值 为核心的代币经济、以九个 行业 为划分的建设度统计，以及依赖行业繁荣度的 股票市场。模组另含每日与活动签到、可管理的系统商城、建设度奖励和多套内置装备玩法。

模组只有一份通用 JAR，全部逻辑在逻辑服务端运行：原版客户端不装任何模组也能进服，通过 26.3 原生 Dialog 使用全部界面。服务器与客户端都安装同一份 JAR 时，/contribution、/stock 与 /shop 会切换为专用的像素绘制界面。

贡献值账户、服务器建设度统计与玩家统计是基本功能。玩家统计与服务器建设度共享同一批已经确认成功的玩家操作事件和同一份去重结果。繁荣度是建设度统计内部根据行业建设度计算的派生指标；股票系统读取繁荣度，但建设度统计不依赖股票。股票买卖、签到、建设度奖励与商城扣款都与账户、流水及各自业务记录处于同一个数据库事务。

跨服事务、幂等与全服定时任务属于所有功能共同遵守的技术约束，不单独构成玩家功能，见 跨服与数据一致性。

三个核心概念

概念是什么谁会产生用途
贡献值账户上的整数代币余额；另有只增不减语义的「历史总收入」管理员发放、签到、建设度奖励、股票卖出、退款、外部 API在系统商城购买物品、在股票市场买入、作为服务器内的通用经济凭证
建设度对有效游玩、建设与生产行为的计量，分九个行业累计玩家操作、机器生产、实体动作、交通距离等折算为贡献值奖励（建设度奖励）、参与繁荣度计算
繁荣度由行业建设度的长期与近期 EMA 推出的相对指标由主服务器在每日结算时计算决定股票的日涨跌修正与退市判定
ℹ
一句话概括你在服务器里做事情产生建设度，建设度按行业累积成繁荣度并定期折算成贡献值；贡献值可以在商城消费、在股票市场投资，而繁荣度决定股票市场的走势。

一局游戏里发生什么

  1. 玩家进服。首次正常进入时自动创建贡献值账户（余额与历史总收入均为 0）。
  2. 玩家采矿、合成、放置方块、种田、经商、跑图。每一类动作按行业标签归入九个行业之一，产生行业建设度；部分动作同时增加玩家个人建设度。
  3. 玩家在线累计满 600 秒，触发当日自动签到，按七日周期领取贡献值。
  4. 每次方块放置或挖掘先计入原始操作次数（玩家统计），再按 20 tick 同位置去重决定是否计入行业建设度。
  5. 每个游戏日 8:00，主服务器结算上一天：累加行业总建设度、更新 EMA 与繁荣度，并据此更新全部股价。
  6. 建设度奖励扫描默认每 300 秒运行一次，把玩家九行业累计建设度按权重折算为贡献值，写入 DEVELOP 流水。
  7. 玩家用贡献值在商城购买物品，或按当日股价在股票市场买入卖出（每日每股各一次，2% 手续费）。
  8. 随机触发的黑天鹅事件会让某个行业的股票在下次结算时固定上涨或下跌 40%。

游戏日与现实时间

模组同时使用两种「天」，混用会造成误判，务必区分：

时间基准定义来源用于
游戏日（核算日）主服务器主世界世界钟。核算日 d=max(0,⌊(T-2000)/24000⌋)，每天 8:00 至次日 8:00 为一天行业结算、股价核算、上市与退市、黑天鹅判定、交易时段
现实自然日配置 rewards.timeZone 指定的时区（默认 Asia/Shanghai）每日签到与活动签到日期
UTC 时间数据库统一存储的现实时间，微秒精度 DATETIME(6)流水时间、归档、筛选条件 from/to
⚠
股票不使用客户端时间股票市场一律信任共享数据库中主服务器发布的观察时钟，子服的本地世界钟不参与交易判定。主服时钟超过 5 秒未更新时，所有服务器暂停交易。

新手最常问的问题

  • 贡献值会不会变负？ 不会。余额与历史总收入都限制在 0 到 231-1，任何会让它们越界的操作都会被拒绝。
  • 为什么我挖了很多方块但建设度没涨？ 可能是该方块没有行业标签、你处于创造模式、或同一位置的连续操作被 20 tick 去重。原始放置/挖掘次数仍会照常累计。
  • 机器生产算我的建设度吗？ 不算。没有明确玩家主体的机器生产只增加服务器建设度，不增加任何玩家的个人建设度。
  • 签到能不能手动领取？ 不能。当天累计在线满 600 秒（默认）后自动签到；活动签到才需要手动 /contribution checkin claim。
  • 股票什么时候能交易？ 第 3 个游戏日开放，每个游戏日 10:00—14:00，对同一支股票当天最多买入一次、卖出一次。

服务端安装

  1. 取得构建产物 code/build/libs/CSU-YSU-contribution-system-<版本>.jar。
  2. 把该 JAR 与匹配版本的 Fabric API 放进服务端 mods/ 目录。
  3. 启动服务器。单人游戏和单服会自动在世界目录建立嵌入式数据库（<世界>/contribution/contribution.mv.db），无需安装数据库服务。
  4. 进服后输入 /contribution 打开贡献值界面，/stock 打开股票市场，/shop 打开商店。
✎
内置数据包自动加载所有玩法定义（配方、进度、装备、行业标签、事件映射）都位于模组 JAR 的 data/contribution/，作为 Fabric 的默认模组数据包在启动/进入存档时加载，不需要安装独立数据包，也不需要手工 /reload。

客户端安装（可选）

客户端模组是完全可选的。未安装的玩家使用 Minecraft 26.3 原生 Dialog，功能与服务端校验完全一致；安装同一份 JAR 后，贡献值、股票与商店会使用专用的像素绘制界面。所有命令在两套界面下都可用。

☀
调试原版界面已安装客户端模组时，可用 /contribution ui_vanilla、/stock ui_vanilla、/shop ui_vanilla 强制回到原版 Dialog，用来复现未安装客户端玩家的体验。重新输入对应的主命令即可恢复自动选择。

版本不匹配的处理

客户端进服时，服务端通过独立的有界版本载荷通知可选客户端自己的模组版本与 Minecraft 版本。客户端比较完整版本字符串，不一致时在聊天框提示双方版本和更新方向，不会强制断线。

  • 原版客户端没有该接收器，服务端不会发送自定义载荷。
  • 能接收旧贡献界面但不能接收版本载荷的旧客户端，由服务端发普通聊天更新提示。
  • 旧服务端没有版本发布机制时无法保证比对，群组服应把所有节点升级到同一版本。
  • 版本检查只在进服时执行一次，不新增按 tick 的查询。

账户身份

每名玩家有且仅有一个账户。在代币系统的语境中，「玩家」即指该玩家的账户。

  • 玩家首次正常进入服务器时自动创建账户；bot_ 前缀的假人（不区分大小写）不创建账户，也不累计签到在线时间。
  • 登录注册只创建新 UUID 的账户，不自动改写已有账户名称。更名或 UUID 变化必须由管理员核对身份后迁移，不能按名称悄悄重绑余额。
  • 支持通过玩家名称或 UUID 查询与操作离线玩家。
  • 使用目标选择器的命令只有在选择器恰好选中一名玩家时才会成功。

流水的归档

  • 在线流水表至少保留一年；超过一年且已完整过期的 UTC 自然月会搬入同库的 contribution_transaction_archive。
  • 归档在主服务器游戏时间 8:00—18:00 运行，每 600 tick 最多搬移 500 条；复制与删除处于同一事务。
  • 流水与幂等 ID 永久保留，归档记录仍可由管理员查询，但不参与普通玩家的即时分页。
  • 未完整过期的月份暂留在在线表中。

幂等与重试

每次操作都具有全局唯一的流水 ID 与幂等 ID，流水表分别为这两个字段建立唯一约束。幂等检查、账户行锁、余额校验、账户更新与流水写入必须在同一个数据库事务中完成。

情况系统行为
幂等 ID 不存在执行操作
操作已经完成返回原操作结果，不重复修改账户
操作正在执行异步调用等待事务结果；IN_PROGRESS 仅作为兼容状态保留，不主动返回
操作失败且事务已回滚使用原幂等 ID 重新执行
⚠
重试必须原样重发网络超时或结果不明时，只能使用完全相同的请求与原幂等 ID 重试。同一幂等 ID 对应的目标、数量、类型、来源、原因、备注或历史收入标志发生变化时，返回 IDEMPOTENCY_CONFLICT。管理员的 /contribution retry 和商店的 /shop retry 就是这一规则的命令入口。

创建账户与 UUID 迁移

/contribution account create <UUID> <玩家名称> 仅当该 UUID 尚无账户、该名称也未被其他 UUID 占用时创建余额与历史总收入均为零的账户。名称冲突不会静默绑定到错误 UUID，而是提示管理员先核对旧账户。

/contribution account migrate <旧UUID> <新UUID> confirm 把旧 UUID 的账户与全部关联数据转到新 UUID。

  • 仅允许在主服务器控制台、该服务器没有在线玩家时执行。群组服运维还应先停止其他子服、备份共享数据库并处理完结果不确定的交易。
  • 目标 UUID 可以没有账户；若已存在，必须是完全空白的账户。有任何余额、历史收入、流水、统计、股票交易、持仓或返还都会拒绝，不会覆盖或合并。
  • 迁移在同一数据库事务和行锁中更新账户、在线与归档流水、玩家统计、交通距离余量、股票持仓与交易、批量请求和退市返还，并写入 account_uuid_migration 审计行。
  • 迁移后，旧 UUID 发出的未完成请求不应继续重试。

假人账户清理

/contribution bot_check 在一笔数据库事务中找出当前名称仍为 bot_ 前缀的账户，并删除账户及该 UUID 的流水、玩家统计、股票持仓与交易、退市返还、签到、商店与奖励记录。

✖
这是破坏性操作该命令不会回滚已经计入服务器全局建设度的历史汇总，清理后也无法从模组内恢复被删的玩家记录。执行前必须备份数据库。非 bot_ 账户不受影响。

管理员增减余额

/contribution add <玩家> <数量> <原因> <影响历史总收入:true|false> [备注]
/contribution remove <玩家> <数量> <原因> <影响历史总收入:true|false> [备注]
  • add 增加余额，remove 减少余额；除备注外其余参数均为必填。
  • 布尔值为 true 时，add 同时增加历史总收入，remove 同时减少历史总收入；为 false 时只改变余额。
  • 管理员不能绕过余额范围和数量范围限制。
  • 每次命令先返回请求 ID 与可点击的原请求重试文本，再异步执行。
  • 成功执行后，operator 记录为 command-<执行者>，source 记录为 contribution:admin_command。
  • 图形界面不提供余额变动入口；旧 ui prepare/confirm 请求会被拒绝执行。

交通距离

  • 移动适配器复用原版服务端的移动统计增量，校验玩家实际处于对应滑翔或乘坐状态，不扫描世界实体。
  • 单次增量超过 16 格时作为异常跳变丢弃；创造与旁观模式不计。
  • 厘米增量转换为百万分之一格的整数进入批次。按「玩家 UUID + 移动方式」保存余数，跨日、离线、重启和跨服继续累计。
  • 数据库事务对余数行加锁，把余数更新、服务器建设度、个人行业建设度和批次幂等标记一起提交。
  • 重载改变距离单位后，尚未折算的真实距离按新单位换算，不清空余数。

方块操作与交互去重

一次放置、挖掘无论影响多少方块位置都按一次操作统计，门和床等不会按部件数量累计。原始玩家放置、挖掘次数不受去重影响，但行业建设度会受影响。

去重键为 K=(s,d,u,a,x,y,z,b)，其中 s 为子服、d 为维度、u 为玩家 UUID、a 为放置/挖掘/交互、(x,y,z) 为本次操作的目标锚点、b 为方块注册 ID。不比较朝向、开关、含水等方块状态；不同动作独立去重；多方块操作只报一个锚点事件。

若 t 为当前 tick、tK 为同键上次成功操作 tick，则只有首次出现或满足 t-tK≥ 20 时才增加行业建设度。

  • 被去重的操作仍会更新上次观察时间，所以连续快速往返操作不会每秒自动获得一次分数。
  • 交互还必须先通过结果检查（方块状态改变或手持物品数量减少）。
  • 服务器与个人行业累计使用同一个去重结果。
  • 缓存只在本服内存保留，每 20 tick 清理过期项，最多 50,000 个键；重启不恢复一秒内的缓存。

核算日与每日结算

主服务器以主世界游戏时钟划分核算日：d=max(0,⌊(T-2000)/24000⌋)，正常核算区间为每天 8:00 至次日 8:00。游戏内睡眠跳时不会错过 8:00 边界；首次安装所在的区间视为不完整日，建设度与累计总量照常保留，但不用于 EMA 初始化；安装前的历史游戏日不补造零值记录。

  1. 主服务器到达新核算日后发布该日规则。
  2. 其他统计服务器每 100 tick 查询一次主服发布的核算日，不使用各自世界时间决定日期。
  3. 子服观察到切日后短暂停止采集，先提交旧批次再切换；跨服观察切日最多约 5 秒加数据库延迟的同步窗口。
  4. 主服务器必须等待所有指定统计服务器确认旧日提交完毕，才结算旧日。未在线或未恢复的统计服务器会阻止结算，不被当作零建设度。
  5. 结算按日顺序追赶，以任务表唯一键和行锁保证重复启动不会重算。一日内九个行业的每日快照、总量、EMA、繁荣度与任务成功状态在同一事务中提交。
  6. 正常结算从 8 点开始，失败重试与历史追赶只在 8:00—18:00 的安全窗口运行；日常事件采集不受该窗口限制。

定义 n 为有效数量、u 为单位建设度，则当日增量 Δ Dd=nu。不设置每日建设度上限；累计值采用 0 至 263-1 的非负整数，达到存储上限时饱和于最大值，不回绕、也不会取消已经成功的游戏操作。

⚠
时间倒退的保护主服时间倒退到数据库已记录日期之前时暂停规则切换，不能覆盖已结算历史。

繁荣度公式

记 xt 为第 t 个完整核算日的行业建设度、Lt 为长期日建设度 EMA、Rt 为近期日建设度 EMA、Pt 为繁荣度。第一个完整日只保存建设度，EMA 为 NULL，繁荣度显示为 0。第二个完整日结束后初始化：

L2=R2=x1+x22

两日均为 0 时也正常初始化。自第三个完整日起：

Lt=0.99Lt-1+0.01xt,   Rt=0.8Rt-1+0.2xt

先更新 EMA，再计算繁荣度：

Pt=0.7Rt-Lt-1Lt+1+0.3xt-Lt-1Lt+1
  • 初始化后两日均为零时，繁荣度为 -1，不是保持未初始化。
  • 任一完整日的零值都参与后续计算。
  • 数据库使用 DECIMAL(30,8)，Java 使用 BigDecimal，中间 EMA 与除法以 8 位小数四舍五入。

统计服务器与游戏模式

  • 只有配置 statisticsServers 列出的服务器采集统计，默认只有 survival；其他服务器不采集。
  • 群组服所有统计服务器连接同一个 MySQL，同一玩家在不同统计服务器产生的数据汇总到同一账户。
  • 玩家行业建设度只接受生存或冒险模式下产生的行为。
  • 原始放置、挖掘次数也记录创造模式的成功操作。
  • 没有明确玩家主体的机器生产只增加服务器建设度，不猜测机器所有者。

热重载与规则快照

主服执行原版 /reload 后解析标签与事件映射，构造不可变的成员快照。跨行业重复对象、未知行业、非法事件、非正整数和可逆 craft 产物都会拒绝整份候选配置，旧配置继续生效；合格候选在下一游戏日 8 点发布，重载不会立刻改变当日行业匹配。

  • 数据库的 contribution_rule_snapshot 按 SHA-256 保存去重后的规则 JSON；contribution_rule_epoch 保存核算日到规则哈希的对应关系。
  • 子服直接使用主服发布的规则快照，不按自己的数据包私自改变行业规则。
  • 启动时加载历史快照，保证旧统计日志仍按原规则重放。
  • 当前 config_version=1 表示规则结构版本，具体业务规则身份以 config_hash 和核算日为准。

玩家统计

总放置、总挖掘与九行业个人累计建设度的统计口径。

  2. 总放置数量

系统定位

玩家统计用于长期记录玩家参与服务器游玩和建设的情况。系统在数据模型和累计语义上模仿原版统计数据，但由服务端模组独立持久化，不直接修改原版统计文件。

  • 群组服行业数据需要通过 MySQL 共享；单服保存在世界内嵌入式数据库中。
  • 原版客户端不包含自定义统计项的名称和界面文本。
  • 统计需要与服务器行业建设度共享去重、行业匹配和批量写入结果。
  • 原版统计值使用 32 位整数，不适合服务器长期累计建设度；模组使用非负 64 位整数（0 至 263-1）。
逻辑标识含义计数单位
contribution:total_blocks_placed玩家累计成功完成的方块放置操作次数成功放置操作
contribution:total_blocks_mined玩家累计成功完成的方块挖掘操作次数成功挖掘操作
contribution:industry_development/<行业路径>玩家在指定行业的累计建设度通过行业规则计算的建设度
✎
这些标识不是原版统计项表中的标识只用于设计和界面说明。当前实现把数值保存在模组数据库表中，并没有把它们注册为原版统计系统的新统计项。

总放置数量

  • 只统计由玩家直接发起并由服务端确认成功的方块放置。
  • 客户端动画、取消事件、放置失败和仅消耗物品但没有产生方块的行为不计数。
  • 按玩家成功完成的操作次数计数：门、床等一次生成多个方块位置的操作仍只累计 1 次。
  • 自动化机器、命令、世界生成、活塞移动、流体扩散和其他环境变化不计入。
  • 统计不要求方块属于某个行业的 place_<行业路径>.json 标签。
  • 同一位置一秒内的重复操作仍计入总放置数量；短期去重只影响服务器与玩家行业建设度。

总挖掘数量

  • 只统计由玩家直接发起并由服务端确认成功的方块破坏。
  • 一次挖掘连带移除多个方块位置时仍只累计 1 次，不按方块位置数或掉落物数量计数。
  • 创造模式直接破坏仍属于玩家成功挖掘，计入总挖掘数量；行业规则可以单独排除创造模式的建设度。
  • 爆炸、机器、命令、活塞和环境变化造成的方块移除不计入。
  • 同样不要求方块带有行业 mine 标签，也不受一秒内去重影响。

玩家行业建设度

玩家行业建设度表示某名玩家通过有效建设行为为各行业贡献的累计建设度，不进行每日重置。合成、放置与挖掘分别通过 craft_<行业路径>.json、place_<行业路径>.json 与 mine_<行业路径>.json 匹配行业，每次事件遵守游戏模式、唯一行业归属和来源计量规则。

方块放置与挖掘必须先通过 20 tick 同位置去重。通过去重后，同一个标准化建设度事件同时增加：对应行业的当日服务器建设度，以及当前玩家在该行业的累计建设度。行业总建设度不在玩家操作发生时直接修改，而是在次日早上 8 点结算时由已完成核算日的当日建设度统一累加。被去重的操作不会增加上述任何建设度；玩家合成没有方块坐标，不适用该去重机制。

事件处理顺序

  1. 服务端确认操作已经成功。
  2. 按本次成功操作增加 1 次玩家总放置或总挖掘统计。
  3. 使用玩家操作标签匹配行业规则。
  4. 执行统计服务器、游戏模式与唯一行业归属校验。
  5. 使用子服、维度、玩家、操作类型、坐标与方块 ID 执行 20 tick 去重；方块 ID 不包含方块状态。
  6. 通过去重后生成一个标准化建设度事件。
  7. 服务器行业聚合器与玩家行业聚合器消费同一个事件。
ℹ
两套统计相互独立某个方块没有行业归属或建设度被去重，不会撤销已经确认的总放置或总挖掘统计。

建设度奖励

如何把个人行业建设度按权重定期折算为贡献值。

  1. 计算公式
  2. 调整权重

计算公式

系统按个人九行业累计建设度定期发放贡献值。令 Di 为玩家在行业 i 的累计建设度、wi 为配置权重、E 为应发放总量、P 为该玩家已经从建设度获得的贡献值：

E=⌊∑i=19 wiDi⌋,   G=max(0,E-P)
  • 九个默认权重均为 1/1000，配置在 rewards.developmentWeights，默认每 300 秒扫描一轮。
  • 升级时，只有九项仍全部等于旧默认值 1/10000 的配置才会自动改写为新默认值；任何自定义权重都保持原样。
  • 主服务器独占扫描任务，按玩家 UUID 每页 32 人顺序处理，计算与数据库写入都在后台线程。
  • 只有 G&gt;0 时才发放；DEVELOP 流水的原因显示「服务器建设」。
  • 余额、历史总收入与 player_development_reward.paid_contribution 在同一事务中增加相同的实际发放量。
  • 余额或历史总收入达到上限时仅发放尚有空间的部分，剩余应发量保留以后再发。
  • 权重降低或建设度不再增长时不会追回已经发放的贡献值。
✎
机器生产不产生个人奖励服务器机器事件只增加服务器建设度，不增加个人建设度，因此不直接产生个人贡献值奖励。

调整权重

rewards 下的九行业发放权重、扫描间隔、现实日时区、签到秒数与周期奖励都在启动时读取。主服务器把这些配置的规范化 SHA-256 指纹写入共享数据库的 reward_configuration 表；每笔发放和购买都会核对指纹，不一致时拒绝操作。

⚠
改奖励配置要全服同步重启修改奖励配置后必须同步所有子服并重启，避免不同子服按不同奖励规则或周期运行。商城商品目录不纳入奖励配置指纹。

签到与活动

每日在线签到

每日签到使用现实自然日（默认时区 Asia/Shanghai），不取 Minecraft 游戏日。任一子服上的在线时间都会计入共享数据库中的同一玩家、同一日期。

  • 玩家当天累计在线满 600 秒（默认）后自动签到，无需手动领取。
  • 服务端约每 20 tick 采样在线玩家，保留不足 1 秒的余量，并在现实日跨日时把完整秒归入对应日期；玩家离线时补计最后一段在线时间。
  • 至多每 60 秒批量落库一次；正常停服会刷入尚未落库的在线时间，异常断电可能损失最后不足一分钟的在线时长。
  • 离线期间不计时；挂机但仍在线会计时。
  • 跨服以同一 MySQL 中的 checkin_daily 聚合，唯一键阻止重复签到。
☀
假人不计时名称以 bot_ 开头的假人不创建账户，也不累计每日在线签到时间。

周期天数第 1 天第 2 天第 3 天第 4 天第 5 天第 6 天第 7 天
默认奖励（贡献值）10101010152525
  • 周期默认 7 天；连续自然日签到推进一天，漏签则从第 1 天重开，完成第 7 天后次日也从第 1 天开始。
  • 签到奖励、日期与周期状态在一笔事务内更新。
  • 奖励为 0 时仍登记签到，但不产生零金额流水。

  • 余额或历史收入已满时暂不标记领取，随后累计的在线时间不会丢失，可在后续在线批次再尝试。

config/contribution/server.json 的 rewards.timeZone、dailyRequiredSeconds、dailyCycleRewards 可分别配置时区、所需在线秒数和各日奖励。

活动签到

管理员在主服务器定义活动 ID、标题、开始与结束现实日期，以及奖励。活动日期采用同一配置时区，起止两日均包含；每名玩家在活动期限内通过 /contribution checkin claim <活动ID> 领取一次。活动签到不要求当天累计在线 10 分钟，与每日签到相互独立。活动定义与领取记录存入共享数据库，群组服不会因切服重复领取。

创建方式命令奖励内容
仅贡献值/contribution checkin event create <id> <标题> <开始> <结束> <贡献值>贡献值，金额可为 0
贡献值 + 物品/contribution checkin event create <id> <标题> <开始> <结束> <贡献值> <物品> <数量>贡献值与原版物品，数量 1—2304
扩展提供者/contribution checkin event create-extension <id> <标题> <开始> <结束> <提供者> <数据>由其他模组注册的奖励提供者决定
  • 贡献值使用 EVENT_CHECK_IN 流水，计入历史总收入。
  • 物品在同一数据库事务内写入 reward_delivery 领取队列；玩家在线时自动尝试交付，也可以用 /shop claim 再次领取。
  • 当前版本只提供创建，不提供直接编辑已经发布的活动；需要变更活动时使用新的活动 ID，以免已领取玩家出现奖励歧义。
  • /contribution checkin events 或贡献值界面可查看当前可领取的活动。

给模组作者的扩展点

其他模组可通过 EventRewardRegistry.register(key, handler) 注册额外奖励提供者，管理员再用 create-extension 创建对应活动。

EventRewardRegistry.register("yourmod:badge", (connection, playerUuid, claimId, data) -> {
    // 使用提供的 connection，在自己的业务表登记 playerUuid 的徽章。
    // 不要在此访问 Minecraft 世界、背包、网络或等待其他线程。
});
  • 处理器在领取事务内执行，只能使用提供的数据库连接，不得访问世界或网络；异常会让整笔活动领取回滚。
  • 提供者必须在服务器启动、玩家领取活动之前注册；未注册的键会被拒绝，对应活动也不能创建。
  • claimId 是本次领取的唯一标识，可作为提供者自己业务表的幂等键。
  • 扩展处理器只应修改自己拥有的表，不得直接修改贡献值账户或流水。
  • 这是额外奖励的扩展点，而不是允许管理员任意执行服务器命令。

当前版本实现系统商店：服务器出售物品，没有系统资金或库存上限。回收、拍卖与抽奖尚未实现。/shop 独立打开商店，原版客户端可以进服并通过 Dialog 购买；安装同一模组的客户端使用专用商店界面。

商品与目录

  • 商品统一保存在数据库的 shop_offer 表中，群组服共享同一个目录。
  • 每件商品自动分配稳定、不可复用的正整数编号。
  • 商品字段包括：名称、物品 ID、完整物品定义 item_spec、每份数量、售价、描述、上架状态、排序值和编辑版本。
  • 名称最多 64 字，描述最多 512 字，每份 1—64 个物品，售价 1—2147483647 贡献值。
  • 物品必须存在于服务器注册表中；排序值越小越靠前，相同排序值按编号排列。
  • 当前最多保留 256 件商品（包含已下架商品），以约束快照大小、查询和客户端筛选开销。

主服务器第一次升级或创建数据库时会自动从 rewards.shopOffers 导入初始商品，并保留旧字符串 ID（如 bread、torch）作为购买与旧订单重试的兼容别名；默认导入面包、火把、铁镐。导入只进行一次，之后重启或修改配置文件都不会覆盖目录。

✎
下架不等于删除/shop take_off 只把商品下架，不会删除商品、历史订单或待发物品，管理员可以再次上架。

管理员操作

OP 等级 2 的玩家可点击商店右上角「管理」，或执行 /shop admin。管理目录显示已上架及已下架商品，选中后点击「编辑商品」；「新建商品」打开完整表单。表单可修改名称、物品及组件、数量、价格、排序、描述及上架状态。

/shop put_on <物品[组件]> <名称> <每份数量> <售价> [描述]
/shop take_off <商品编号>
/shop modify <商品编号> [名称] [每份数量] [售价] [描述]
  • put_on 自动分配编号并上架，排序默认 0。
  • modify 按名称、数量、售价、描述的顺序填写；只修改后面的字段时，前面填 - 保持不变，未填写的尾部字段不变；描述填 "" 清空。
  • 中文名称或含空格的名称用引号；描述可直接填写多个词。
  • 物品、状态和排序可以在完整管理表单中修改。
  • 保存时校验编辑版本：其他管理员已经修改时拒绝覆盖，并保留输入供修改或重读。
  • 原版 Dialog 的模板转义有限：名称和描述不要含双引号、反斜杠；复杂文字用正确转义的管理员命令填写。
/shop modify 4 - - 35     # 只修改售价，其余保持不变

购买与交付

  • 购买使用共享数据库的当前商品记录；商品行锁保证与编辑同步。
  • 客户端界面附带商品版本，目录过期时拒绝成交并提示刷新，不按玩家没看到的新价格扣款。
  • 文字命令省略版本时，以服务器当时的商品价格成交。
  • 余额不足或商品已下架时不扣款、不创建订单或流水。
  • 单笔 1—64 份，最多 2304 个物品，总价不超过 231-1。
  • 成功时在同一事务中锁账户、扣款、写 SHOP_BUY 流水、创建 shop_order 与 reward_delivery。购买不影响历史总收入。
  • 订单有全局唯一 ID；结果不明时用 /shop retry <订单ID> <商品ID> <份数> 沿用原请求。即使之后商品改价或下架，已提交订单仍返回原结果，不重复扣款或创建待发记录。换玩家、商品或份数使用同一订单 ID 会被拒绝。
⚠
交付不是严格一次待发物品队列支持断线、背包已满和跨服后领取，背包放不下的剩余物品掉落在玩家附近。数据库使用短租约避免多服同时交付同一待发项，但游戏背包与 SQL 不能加入同一原子事务：服务器在物品已进入背包但确认未入库时崩溃，仍存在重复交付的极小窗口。

自定义物品组件

上架及编辑物品使用 26.3 原版 ItemArgument/ItemParser，与 /item ... with <物品> 的物品参数相同，不自行拆分 JSON/NBT。支持附魔、自定义名称、属性、模型、药水、耐久、自定义数据以及 !组件 删除默认组件。数量独立由「每份数量」字段定义，不要在物品定义中混入 count。

/shop put_on minecraft:diamond_sword[minecraft:custom_name={text:'荣誉剑'},minecraft:enchantments={'minecraft:unbreaking':3}] "荣誉剑" 1 100 纪念装备
  • 完整定义最多 2048 个字符；未知组件、无效组件值及尾随内容会被原版解析器拒绝。
  • 数据库仍保留纯注册表 ID 用于查询，并另存完整定义。
  • 购买时把完整定义拷贝到待发记录，与扣款在同一事务内完成；之后编辑或下架商品不会改变已付款的物品。
  • 交付在服务器主线程用当前注册表解析一次，按组件指定的最大堆叠数拆分副本，保留全部组件。
  • 解析失败不发出普通物品替代，也不丢弃待发记录，记录警告留待管理员排查。
  • 跨服必须安装相同注册项、数据包与模组。旧活动奖励和旧待发记录仍支持普通物品 ID。

性能

  • 目录、编辑、购买都在现有有界数据库线程池中执行，不阻塞游戏主线程。
  • 服务器仅在玩家请求时读取商品快照；客户端搜索或排序变化时重建缓存，不逐帧访问数据库或重新排序。
  • 每页只注册当前容量的卡片控件，滚动复用这些控件。
  • 客户端商品图标按完整定义预览，最多缓存 512 个样品，离服清空。
  • 文本快照最大长度提升至 1 MiB 以容纳目录中的组件信息；目录数量仍最多 256 件。

市场基础

  • 股票系统依赖行业建设度系统提供的繁荣度。
  • 使用与账户相同的数据库：单服默认嵌入式 H2，群组服使用共享 MySQL。买卖和每日核算只在服务端执行。
  • 股票在第 3 个游戏日开放。
  • 每个游戏日早上 8 点更新股价，更新后的价格即为当日股价。
  • 同一交易日保持 20 支股票；有空位时当天 8 点补齐。由旧版 30 支股票升级时，多出的股票在下次 8 点进入退市状态，并在当天 14 点完成退市。
  • 每个行业至少有一支股票。
  • 股票从内置的 36 个原版物品符号中选择，每行业 4 个候选；物品只用作股票名称与标识，交易不消耗或发放对应物品。

交易规则

规则内容
交易时段每个游戏日 10:00—14:00（对应约 200 秒现实时间）
每日次数每名玩家对每支股票每天最多买入一次、卖出一次；各服共享这项限制
当日买入的股票当日不能卖出
单一股票持仓上限10,000 股
单次交易数量1—10000 的整数
手续费买入与卖出均收取成交额的 2%（四舍五入到整数）
交易对手玩家直接与系统按当日股价即时交易，没有玩家之间的挂单撮合
系统库存不维护资金池和有限股票库存；股票没有固定总发行量

令 Q 为交易数量、P 为当日股价，则基础成交额 C=Q× P，手续费 F=round(0.02C)；买入应付 Cb=C+F，卖出到账 Cs=C-F。

  • 金额计算使用 64 位整数作为中间结果，但账户变动必须符合有符号 32 位范围。
  • 买入与卖出均不改变历史总收入；卖出仅增加当前余额。
  • 买入时，玩家支付的代币与手续费被销毁并转换为持股数量；卖出时，系统按成交额扣除手续费后增加代币并减少持股。

交易前校验

条件反馈
买入应付金额大于余额余额不足
买入后持股超过 10000持仓达到上限
卖出数量大于当前持股持仓不足
卖出后余额超过 231-1数值溢出
主服务器市场时钟超过 5 秒未更新所有服务器暂停交易
观察时钟所属核算日尚未完成股价更新暂停并提示等待核算

所有校验、账户与持仓更新、贡献值流水、股票交易流水在同一数据库事务中进行。校验失败时不改变余额或持股，也不写入流水。每笔交易生成全局唯一幂等 ID；重试必须复用原 ID，相同 ID 的不同参数会被拒绝。

上市与退市

每个游戏日早上 8 点，按随机顺序从 36 个候选物品中补齐所有空位，优先覆盖当前缺失的行业。最近退市的 5 种物品不能上市；新股上市后的前 3 天不参与退市判定。每只新股独立从闭区间 [100,400] 等概率抽取整数作为上市初始股价 p0。

新股上市 3 个游戏日后开始检查退市，满足以下任一条件即在当天进入退市状态：

  • 股价降至退市阈值 pd=max(0.5p0,0.25ph)，其中 ph 为截至当日的历史最高股价；整数比较使用 max(⌊ p0/2⌋,⌊ ph/4⌋)。
  • 某行业连续 7 个游戏日繁荣度最低时，从该行业中选择「当前股价／上市股价」最低的可退市股票；该行业在触发日之后的 6 个游戏日内不会再次通过此条件触发退市。
  1. 触发日 8:00 标记为 RETIRING，不再接受买入；10:00—14:00 可以按当天正常股价手动卖出，没有随机失败率。
  2. 当天 14:00 交易窗口结束时，剩余持股按当前股价的 50%（四舍五入）自动返还，不收手续费，清空持仓并标记 DELISTED。离线玩家也在同一数据库事务中入账；返还不计入历史总收入。
  3. 余额上限导致暂不能全额入账时，余款保留，可用 /stock claim 再领。若游戏时间被跳过或服务器中断，主服务器恢复后按已确定的最后股价补做结算。

令 P 为退市当日股价、Q 为窗口结束时剩余股数，应返还额 R=round(0.5PQ)；实际立即入账额还受账户余额上限约束。

界面

输入 /stock 打开股票大厅。安装同一 JAR 的客户端收到服务端快照后，显示独立的股票屏幕：列表不分页、可滚动查看全部 20 支股票；每只股票占 55 个 GUI 逻辑像素高，展示名称、行业、现价、当日涨跌值与比例、持仓、历史高低、退市阈值及当前价格与阈值之比，并绘制真实的逐日股价曲线。

  • 市场列表的曲线横轴始终代表截至当前游戏日的 30 个游戏日；上市不足 30 日的股票只占右侧已有记录对应的时间段，不拉伸至整个宽度。
  • 上涨用红色、下跌用绿色；当日涨跌为 0% 时沿用最近一次非零涨跌的颜色，从未变动过才使用中性色。
  • 可搜索股票名或物品 ID，可逐项点击控件单选/多选行业、切换仅持仓；可按名称、价格、当日涨跌幅、退市阈值倍数、持仓和上市时间排序。
  • 曲线以单像素宽的正交连通路径连接相邻每日价格，陡峭波动时不靠加粗笔画补缝。
  • 刷新只更新数据并保留本次打开期间的搜索、筛选、排序、滚动、数量和选股状态；完全退出后再次打开恢复默认设置。
  • 未安装模组的原版客户端通过 26.3 原生 Dialog 在同一可滚动页面列出全部 20 支股票，详情页用 Braille 文字曲线绘制，明确标为后备展示。
☀
列表与导航细节股票行第一列左对齐显示股票名与编号、行业，以及小型「详情」按钮；单击小按钮进入详情，双击行仍是快捷方式。详情页或个人页按 Esc 等同「返回市场」，市场页按 Esc 才完全退出股票界面。滚动条只显示，不支持拖动，使用鼠标滚轮滚动。

批量交易

  • /stock batch <buy|sell> <数量> <逗号分隔的股票ID> 逐只执行，最多 20 只、编号不可重复，不是全批原子事务。
  • 编号以数值去重，因此 1,01 不会被当成两只股票；原参数文本仍用于重试身份校验。
  • /stock batch-retry 使用原批次 UUID 重试未完成的股票交易，side、数量、编号及顺序必须保持原请求。

每日执行保障与通知

  • 股价核算和新股上市统一在主世界游戏时间早上 8 点执行；退市持股结算改在触发日 14 点执行。
  • 先等上一个行业核算日结算成功、取得繁荣度，再按行业排名更新噪声与股价、处理退市、补足上市空位。
  • 主服务器约每 20 tick 从 minecraft:overworld 世界钟采样并写入独立的观察时钟；客户端刷新与实时推送都以该时钟显示游戏日与时间。
  • 子服约每秒从共享数据库读取一次观察时钟再推送给本服在线客户端，而不是按玩家逐个查询。
  • 系统不依赖某一 tick 恰好为 8 点：发现未核算的游戏日时，主服务器通过 stock_market_state 单行锁和同一事务执行一次过渡；落后多日则逐日追赶。
  • 首次在已有世界启用时从当前游戏日开始上市，不虚构安装前的历史股价。
  • 持有接近退市阈值或已进入退市状态的股票时，系统为持有人写入聊天提醒；14 点自动退款时另写入退款与待领余款提醒。各子服约每 10 秒领取本服在线玩家的未投递通知，因此切服与离线后仍可收到。
⚠
通知可能漏发，金额不受影响数据库通知状态与聊天发送不能组成同一原子事务，极端崩溃窗口可能造成个别提醒漏发；账户与退款金额不受影响。

变量与参数

符号含义
pt第 t 个交易日的股价
p0上市首日的初始股价，来自 [100,400] 的等概率整数
pmax该股票允许达到的最高股价，等于 10p0
Nt第 t 个交易日的 OU 噪声
Bt第 t 个交易日的波动基准
wt第 t 个交易日由行业排名确定的修正参数
Zt每只股票独立抽取的标准正态随机数

每支股票独立维护 OU 噪声与波动基准。上市时 N0=0，长期均值为 0、时间步长为 1、θ=0.35、σ=0.8。每个新交易日按下式更新噪声，状态随数据库持久化，重启后继续：

Nt=(1-θ)Nt-1+σ Zt,   Zt∼N(0,1)
B0=0.1p0,   pmax=10p0

每日更新公式

当 Nt&gt;0 时：

pt=clip(pt-1+0.1Nt(1+wt)Bt-1, 0.3pt-1, min(3pt-1,pmax))

当 Nt≤ 0 时：

pt=clip(pt-1+0.1Nt(1-wt)Bt-1, 0.3pt-1, min(3pt-1,pmax))
  • 股价使用整数，公式计算后四舍五入；下限至少为 1，上限不超过 pmax。
  • 旧存档中已超过新上限的股票会在下一次日核算时直接裁剪至新上限。
  • 随后用 0.1pt 对波动基准执行 EMA 更新：Bt=0.9Bt-1+0.1(0.1pt)。
  • 波动基准和噪声以 8 位小数保存。

黑天鹅事件

随机玩家与三个行业的考察窗口，以及固定 40% 的股价修正。

  1. 事件流程
  2. 影响哪些股票
  3. 固定修正公式
  4. 消息播报

事件流程

黑天鹅事件只由主服务器判定，状态与结果保存在共享数据库中。模组首次运行后，从下一个游戏日 8:00 开始尝试：

  1. 在 8:00—10:00 之间随机选一名主服务器在线的非假人玩家，并从九个内置行业中随机选三个不同的行业。若该时段无人在线，顺延到下一游戏日。
  2. 判定窗口持续 2 个游戏小时（2000 游戏刻）。
  3. 所选玩家在任一候选行业的个人累计建设度相对窗口开始时增加，就视为参与该行业的服务器建设；仅服务器机器事件、不属于该玩家的建设度不满足条件。
  4. 为等待统计批次写入，窗口结束后最多延迟 100 刻读取共享数据库；实际判定以读到的累计值为准。
  5. 同一玩家在多个候选行业都有增长时，选择增长最多的一个；相同增长量时按行业 ID 排序选择第一个。
  • 若选出一个行业，只有该行业发生好天鹅事件；否则三个候选行业都发生坏天鹅事件。
  • 判定完成后随机等待 6—80 个游戏日，在其后的 8:00—10:00 发起下一轮。
  • 事件、候选行业、下次启动日与是否已用于结算均持久化，主服务器重启不会重新抽签或重复修正价格。

影响哪些股票

  • 好天鹅影响该行业在下一次结算时仍在市场的所有股票。
  • 坏天鹅在判定完成时，从每个坏事件行业当前仍在市场的股票中等概率随机选一只，通常三个行业对应三只股票；其他同行业股票仍按普通股价算法结算。
  • 坏事件目标编号与结果一起持久化，重启和结算重试不会重新抽选；该行业没有股票时不选目标，目标在结算前退市时不另选替代股票。
  • 升级前尚未应用的坏事件在首次结算前补选一次并保存。

固定修正公式

在判定后的下一次 8:00 股价核算，上述目标股票跳过普通涨跌结果，以核算前一天股价 pt-1 为基准执行固定修正：

pt=clip(round(1.4pt-1),1,10p0) （好天鹅）
pt=clip(round(0.6pt-1),1,10p0) （坏天鹅）
  • 整数四舍五入与初价 10 倍上限仍然生效。
  • 修正后的价格正常进入历史曲线、波动基准与退市判定。
  • 同一事件不会在后续结算重复生效。

消息播报

判定后的三个游戏日内，客户端股票页面标题左侧仍为「股票市场」，主世界游戏日、时间和交易状态在右侧，中间滚动显示事件。原版客户端的股票 Dialog 把同样的消息列为市场消息，不支持动画滚动。

事件消息模板
好天鹅「由于 XXX 在 XXXX 行业的杰出贡献，XXXX 行业股市繁荣增长」
坏天鹅「由于 XXX 在 XXXX 行业的无所作为，XXXX 行业股市动荡不安」

多个仍有效的事件会串联滚动显示。

  • 所有玩法定义位于模组 JAR 的 data/contribution/，作为 Fabric 的默认模组数据包在启动/进入存档时加载；不需要安装独立数据包或执行 /reload。

结构

新树根为 contribution:items/root，标题为「更多乐趣」。已重接缺失的父节点，不迁入 impossible/函数/全局计分板成就。每项只依靠自己的 advancement JSON，没有额外函数或自定义标签。

26.3 的触发器实体字段使用显式 entity_properties，实体子谓词采用命名空间键；羊色/美西螈变种匹配原生组件。伤害类型直接引用具体 damage_type；位置条件是显式 all_of/any_of，不使用旧隐式数组。

资源包与外观

内置外观资源包的生成、导出与分发给原版客户端的方式。

  3. 包含的纹理

为什么要额外分发

模组只通过服务端逻辑提供物品规则，不会擅自把资源推送给原版客户端。安装同一模组的客户端会自动加载 assets/contribution/ 下的外观；未安装客户端模组的玩家必须由服务器通过原版资源包机制另行分发，才能看到主题贴图与添翼外观。

资源包的生成与导出

  • 构建时生成 code/build/libs/CSU-YSU-items-<版本>-resource-pack.zip，同时内嵌于 JAR。
  • 启动时自动导出到 <世界>/contribution/resource-packs/CSU-YSU-items-<模组版本>.zip。
  • 已有同版本文件不覆盖；更新版本会生成新文件。
  • 本模组不擅自开启 HTTP 端口、修改防火墙或覆盖现有服务器资源包。

由管理员把 ZIP 放到已有资源包分发地址，并按原版 server.properties 的 resource-pack 与 resource-pack-sha1 设置发送；若已有其他资源包，应合并后分发。require-resource-pack=false 可允许玩家拒绝外观包仍进入。

包含的纹理

  • 复用用户提供的 22 张主题 PNG，另将三张成人装甲纹理复用到婴儿装备层，共 25 张打包纹理。
  • 0.1.6 另复用六张添翼图层 PNG、十八张透明翅膀纹饰 PNG，并复制原版青色混凝土粉末为独立 GUI 背景，共 50 张打包 PNG。
  • 补充十八种原版图案缺失的 minecraft:textures/trims/entity/wings 透明纹理，保留胸甲纹饰、不在翅膀叠加纹饰，修复紫黑贴图；不覆盖 atlas。
  • 新进度树背景引用 contribution:gui/advancements/backgrounds/cyan_concrete_powder，避免旧格式 textures 前缀被重复展开。

本地开发工作流

run-gradle.ps1 build 成功后会自动备份并替换两处 JAR，以及指定客户端 resourcepacks 中本模组的旧 ZIP；不修改其他资源包或 options.txt。客户端须在选项中选择新版本资源包。

两套界面如何选择

  • 安装本模组的客户端使用可选的像素对齐页面；未安装模组的原版客户端继续使用 Minecraft 26.3 原生 Dialog。
  • 服务端始终负责查询与权限验证；原版客户端无需安装模组。
  • 股票和商店同样各有可选客户端页面及原版 Dialog 后备界面。
  • 输入 /contribution 或 /contribution ui 打开首页；安装客户端模组时，账户与统计、流水、行业、签到、管理员查询、账户列表和查询结果都使用同一套客户端页面，不在跳转时自动切回 Dialog。
  • 文字命令与聊天分页保留，控制台继续使用文字命令。

筛选与分页

  • 客户端流水页可点选「全部」「股票买入」「股票卖出」等常用筛选；原版流水页保留「全部流水」「股票买入」「股票卖出」「管理员调整」「退市返还」按钮。
  • 其他筛选仍可使用 type/source/server/from/to 的 名称=值 高级格式，与文字命令共享解析及权限。
  • 筛选日期按 UTC 日界线计算并包含结束日期，界面会注明该区别。
  • 普通玩家只能查询本人最近 90 天；管理员可查历史归档，单次最多 365 天。
  • 分页游标历史独立存储，只有「上一页」使用该历史；Esc 不返回上一页流水。

导航模型

  • Esc 指向语义上级，不把翻页当上级；首页 Esc 退出。
  • 翻页只更新模块内容，不改变上级。
  • 所有贡献页底部固定「返回上级、首页、关闭」，关闭立即退出并使旧查询失效。
  • 原版子页的取消动作同样指向上级：股票详情/个人页指向市场，商店编辑指向商品管理，商品管理指向商店。
  • 纯页面导航不经过交易请求限流；异步查询返回时若玩家已切到其他页面，旧结果会被丢弃，避免覆盖新画面。

设计依据：NN/g 关于层级导航（面包屑表示层级路径而非访问历史）与 W3C 一致导航（重复导航维持顺序）的通用要求。实现采用固定上级、独立分页与固定关闭入口，并不声称这是唯一适用的 UI 方案。

布局与控件细节

  • 每位玩家只有一个服务端 PageSession，集中保存页面、导航、模式、请求间隔、版本及在途读取；异步结果必须同时匹配会话对象和页面版本。
  • 账户列表与活动行使用注册的 AbstractWidget 接收点击，支持悬停边框、手形光标和键盘聚焦，不依赖屏幕手写坐标判断。
  • 滚动时复用当前可见行控件；同一模块刷新、翻页、搜索复用同一 Screen 实例并更新数据/控件绑定，保留输入与焦点，不调用 setScreen 创建新页面。
  • 内容区按实际按钮行数计算，避免第三行按钮覆盖表格；窄屏流水按比例分配列宽，行业总览五列等宽。
  • 合并账户页的账户摘要、原始操作统计和行业建设度分区绘制，超出高度时滚轮滚动并显示只读滚动条。
  • 所有滚动条只显示，不支持拖动；使用鼠标滚轮滚动。
  • 客户端贡献页面不暂停单人世界；首页关闭会使服务器待完成的查询失效。
☀
数据延迟说明数据从当前数据库异步读取，不阻塞服务器线程；界面反映已提交的数据，统计正常有约 5 秒批量提交延迟。数据库不可用时显示错误页，并按本地文件库或共享 MySQL 给出不同排查提示，不显示缓存余额冒充实时余额。

文件位置与格式

  • 运行配置使用 UTF-8 JSON，默认路径为 config/contribution/server.json。
  • 该文件已被 .gitignore 排除，不要提交含口令的副本。
  • 数据库口令可以写入仅服务器可读的配置文件，也可以由环境变量 CONTRIBUTION_DB_PASSWORD 覆盖。
  • 日志和错误反馈不得回显口令，也不会打印完整 JDBC URL。

字段分组

分组关键字段生效方式
数据库database.mode（embedded / mysql）、地址、凭据、连接池大小、工作线程数启动时读取，修改需重启
服务器身份serverId、mainServer、statisticsServers启动时读取，修改需重启
奖励与签到rewards.developmentWeights、扫描间隔、rewards.timeZone、dailyRequiredSeconds、dailyCycleRewards启动时读取，且写入共享数据库指纹，各服必须一致

✎
旧配置的兼容推断旧配置没有 mode 字段时：enabled=true 自动按 MySQL 读取，enabled=false 自动按嵌入式模式读取。

奖励配置指纹

主服务器把奖励相关配置的规范化 SHA-256 指纹写入共享数据库的 reward_configuration 表；每笔发放和购买都会核对指纹，不一致时拒绝操作。修改这些配置后应同步所有子服并重启。

  • 纳入指纹：建设度权重与扫描间隔、现实日时区、签到秒数与周期奖励。
  • 不纳入指纹：商城商品目录（价格与商品以共享数据库为准）。
  • 纳入指纹的配置改变后，各服不一致会导致购买与发放被拒绝。

备份方式不同单服可以整体备份世界目录下的 contribution/ 文件夹；群组服必须另行备份 MySQL 数据库，只复制各子服的本地目录会丢失权威数据。备份前先停服，不要在运行时复制数据库文件，也不要手工编辑 .mv.db。

迁移的执行者

  • 单机嵌入式库：首次启动自动创建数据库文件与业务表，之后每次启动执行迁移。
  • 群组服：只有生存服或独立部署流程可以执行 MySQL 迁移，其他子服启动时仅执行 validate。
  • 子服发现结构版本不匹配时会拒绝启用数据库功能，避免多个子服并发修改表结构。
  • 迁移失败时经济与统计服务保持不可用，日志给出迁移版本与错误摘要（不含口令）。
  • 破坏性迁移必须先备份，并在维护窗口由管理员显式执行。

    主服务器与统计服务器

    • 群组服不设置大厅服：生存服是主服务器，并承担原本大厅服的作用。
    • 群组服所有子服必须连接同一个 MySQL，账户表与流水表都使用 InnoDB。
    • 建设度与玩家统计只在 statisticsServers 列出的服务器采集，默认只包含生存服。
    • 子服每 100 tick 同步主服发布的核算日与规则。相同规则的日期推进不等待全部缓冲清空；真正改规则仍需完整排空。旧日关账只等待该日及更早批次，主服等待全部指定服务器确认后结算。
    • 无论配置多少个统计服务器，每日结算仍只由生存服执行。

    原子事务与幂等

    每次代币操作必须在同一个数据库事务中完成账户更新与流水写入，任意一步失败则整个事务回滚。修改账户前使用 SELECT ... FOR UPDATE 对目标账户加行锁，在持有行锁期间完成余额校验、账户更新与流水写入。

    以下操作全部遵守幂等规则：管理员命令、签到、建设度奖励与商店订单、股票交易、外部 API。一次操作发生重试时必须继续使用原幂等 ID。

    全服级定时任务

    • 全服级定时任务只在生存服运行：其他子服不执行建设度日结算、股价更新和建设度奖励全服扫描，也不参与定时任务选主。
    • 所有基于游戏日的全服核算统一在主世界游戏时间早上 8 点执行。
    • 生存服不使用分布式选主。
    • 每个任务记录任务日期、状态和唯一任务标识，防止重启后重复执行；同时保存尝试次数、更新时间、租约截止时间、完成时间和失败代码。
    • 重启后只接管租约已经过期的 RUNNING 任务，并在同一记录上增加尝试次数，不新建第二条同日同任务记录。
    • 当前结算事务失败时整体回滚，保留 RUNNING 记录，等待 5 分钟租约过期后接管重试。
    • 未收到全部子服关日确认时不创建结算任务。
    • 现实日在线签到不属于全服核算任务：每台玩家所在服务器只累计本服玩家在线时间，汇总到共享数据库，由唯一日期键和事务阻止重复发奖。

    数据库不可用时

    数据库不可用时拒绝以下经济写入：代币增减、签到、股票交易、商城交易与建设度奖励发放。玩家会收到：

    [贡献值] 数据服务暂时不可用，请稍后重试
    • 数据库连接失效后每 600 tick 尝试重建；恢复后经济功能自动恢复。
    • 确认未执行的拒绝请求不会自动补录。
    • 若提交时连接中断，模组先用原幂等 ID 查询已提交流水；仍不能确认时，调用方必须使用原请求与幂等 ID 重试，不能直接认定未扣款。
    • 图形界面对嵌入式数据库与共享 MySQL 的不可用状态显示不同的排查提示。
    ☀
    玩家侧排查建议出现「数据服务暂时不可用」时：单服检查世界目录下 contribution/ 是否可写；群组服检查主服在线、MySQL 可达与凭据是否正确。余额不会被缓存显示，界面会明确报错而不是显示旧值。

    统计批次的可靠性

    • 高频统计先在执行操作的服务器内存中聚合，再通过带全局唯一批次 ID 的批次写入数据库。
    • 已捕获积压批次在提交回调后继续处理下一批，不在批次之间额外等待五秒；回调不捕获当天新缓冲，仍保持单个在途任务。旧日关账每事务最多32日，行业和股票按日追赶。
    • 恢复保留原日志、批次ID与日期，不重算已完成流水，也不能恢复采集暂停期间从未记录的行为。群组服需要全部统计节点升级并提交关账；缺失节点、规则哈希不符和快照缺失仍安全阻塞。
    • 每个批次同时保存规范化内容的 SHA-256 payload_hash；重试必须继续使用原批次 ID 与原哈希。
    • 同一批次 ID 携带不同哈希时拒绝处理并记录错误，不能当作成功重试。
    • 统计批次与代币交易相互独立：数据库不可用时代币交易必须拒绝，而建设度统计进入有界内存缓冲并同步写入本地恢复日志。

    日志与审计

    级别内容
    INFO启动版本、配置摘要、迁移结果、数据库状态切换、每日结算和统计批次汇总
    WARN重试、队列接近上限、恢复日志增长、非法配置和可降级故障
    ERROR迁移失败、数据一致性失败、恢复日志损坏和无法回滚的异常
    DEBUG开发环境中的请求路径和性能数据，默认关闭
    • 账户流水是权威审计记录；日志只记录流水 ID、幂等 ID、操作类型、来源、服务器 ID、耗时和结果状态。
    • 数据库口令、完整连接串、聊天备注和其他可能含敏感信息的文本不得进入普通日志。
    • 普通成功事件不逐条写日志，批次汇总、状态切换和异常使用限频日志，避免玩家活动放大磁盘写入。

    公开排行榜

    /contribution leaderboard

    贡献首页的排行榜入口默认展示富豪榜（当前贡献余额）。可切换历史贡献（历史总收入）、总建设度与九行业建设度。客户端UI和原版Dialog都可用，玩家公开查看名次、玩家名称与数值，不包含他人UUID或私有账户详情。

    每榜前100名、每页8名，15秒共享缓存；同值按UUID稳定排序，名次为顺序序号。建设度只统计九行业已入库的正值，零值、未知行业和bot_账户不参建设度榜；贡献榜包含零余额/收入账户。总建设度精确求和，不发生long溢出。缓存期内刷新不会重新读库。

    富豪榜Esc返回首页，其他综合榜返回默认富豪榜，行业榜返回行业列表；翻页不成为返回上级的目标。所有榜页保留显式关闭与类别切换。

    管理员自动诊断

    /contribution diagnose

    管理员（OP 2）或控制台执行；原版客户端也能在聊天栏收到报告。异步检查数据库、主服时钟归属/新鲜度、规则、统计缓冲、关账与核算进度，触发正常服务的恢复请求。每实例一个会话，15秒冷却；初次报告后100 tick（正常约5秒）复查，游戏或空服暂停时等待恢复运行。

    ✎
    自动修复的安全边界仅重连、提交缓冲与重试规则/时钟/核算；不删除数据、不跳过关账、不改写历史、不强制解锁。主服配置冲突、日期回退、缺失节点、哈希不符或历史快照缺失会明确报告，需人工处理。仍遵守8:00—18:00核算窗口，不等同于UI或网络故障测试。

    已知边界与风险

    • 持仓加权成本仍按用户历史交易重放，时间 O(t)，不是常数；增量物化需要新的迁移、历史回填与事务一致性设计。
    • 背包交付与 SQL 无法组成同一原子事务，极端崩溃窗口可能重复交付；已有租约降低并发风险，但不声称严格一次。
    • 每秒市场时钟发布与跨服读仍有数据库负载；不能把同步周期改长而破坏交易时段准确性。
    • 0.1.10在双端 logs/latest.log 增加每分钟限频诊断。服务端记录主世界钟、规则日期、缓冲、市场和行业已结算日及各服关账；缺失关账日志指出具体日期和服务器。客户端记录载荷大小、时钟序号和新鲜度，解析异常保留堆栈，不输出完整载荷或口令。
    • 先前「客户端卡死/连接超时」未获得充分的生产复现证据；会话重构与生命周期测试不等于确认原始卡死根因已消除。
    • 未提供未经实测的 MSPT 降幅结论。上线后应记录玩家数、数据库延迟/慢查询、队列拒绝、统计日志增长、客户端/服务端同期异常。

    入口与依赖

    • 模组通过 cn.contribution.api 包提供稳定的公共 API。其他模组只能依赖该包，不应直接访问账户仓库、数据库连接、流水服务或其他内部实现。
    • 公共入口为 ContributionApi；API 只能在逻辑服务端调用。
    • Contribution 尚未发布到 Maven 仓库时，可以把开发 JAR 放进调用模组的 libs 目录并用 compileOnly 引用。
    • API 不分别提供 add 和 remove 函数：所有余额变更统一通过 changeBalance 提交，使数值校验、余额检查、历史总收入更新、幂等检查和流水写入无法被调用方绕过。
    CompletableFuture<BalanceChangeResult> changeBalance(
        BalanceChangeRequest request
);

    请求字段

    字段类型说明
    idempotencyIdUUID调用方为一次业务操作生成的全局唯一幂等 ID
    targetAccountTarget通过玩家 UUID 或玩家名称指定的单个账户；API 不接受目标选择器
    amountint带符号的余额变动量；正数增加，负数减少，不能为 0
    typeBalanceChangeType目前支持 EXTERNAL 与 REFUND
    sourceIdentifier调用来源，例如 quest_mod:quest_reward；字符串形式最多 128 个字符
    reasonString流水原因，最多 64 个 Unicode 字符
    noteString可选备注，最多 64 个 Unicode 字符
    affectTotalIncomeboolean是否将带符号的 amount 同步作用于历史总收入；退款必须为 false

    EXTERNAL 允许正向或负向变动。旧的七参数构造器保留原默认规则：正向 EXTERNAL 计入历史总收入，负向 EXTERNAL 不影响历史总收入；新的八参数构造器可明确传入 affectTotalIncome。REFUND 的 amount 必须为正数，且 affectTotalIncome 必须为 false。

    返回状态

    状态含义
    SUCCESS操作成功，或幂等重试取得了原成功结果
    ACCOUNT_NOT_FOUND玩家名称或 UUID 对应的账户不存在
    INVALID_AMOUNT数量为 0、超出范围，或不符合操作类型要求
    INVALID_TEXT原因、备注或来源标识不符合要求
    INSUFFICIENT_BALANCE扣款后余额将小于 0，或历史总收入将小于 0（反馈「历史总收入不足」）
    BALANCE_OVERFLOW操作后的余额或历史总收入将超过 231-1
    DATABASE_UNAVAILABLE数据服务不可用或结果暂时无法确认；必须沿用原幂等 ID 重试
    IN_PROGRESS为兼容保留；当前实现不会主动返回该状态
    IDEMPOTENCY_CONFLICT相同幂等 ID 被用于内容不同的请求

    参数错误、余额或历史总收入不足等可预期的业务失败通过 BalanceChangeResult 返回，不使用异常表示。结果中的可选数值使用 OptionalInt，流水 ID 使用 Optional<UUID>，不使用 0 或负数作为缺失值。兼容版本可以增加新的结果状态，因此调用方处理状态时必须保留未知状态分支。

    异步与线程规则

    • changeBalance 异步执行数据库操作。调用方不得在服务器主线程使用 join()、get() 或其他阻塞方式等待结果。
    • CompletableFuture 的完成回调不保证位于服务器线程；需要修改世界、访问实体或向玩家发送消息时，必须通过 MinecraftServer.execute 返回服务器线程。
    • 客户端界面需要修改余额时，必须先向服务端发送经过校验的请求，再由服务端调用 API。
    ContributionApi.getInstance()
        .changeBalance(request)
        .thenAccept(result -> {
            server.execute(() -> {
                if (result.successful()) {
                    // 使用 result.balanceAfter() 反馈余额
                } else {
                    // 使用 result.message() 反馈失败原因
                }
            });
        });

    幂等与重试

    1. 创建并持久化业务记录与幂等 ID。
    2. 构造不可变的 BalanceChangeRequest。
    3. 调用 changeBalance，不阻塞服务器主线程。
    4. 检查 BalanceChangeStatus。
    5. 仅在 SUCCESS 之后执行依赖余额变更成功的后续操作。
    6. IN_PROGRESS、超时或 DATABASE_UNAVAILABLE 后，使用原请求重试。
    7. 业务失败时保留原结果，不使用新幂等 ID 暗中重做同一操作。
    ✖
    不要在重试时生成新 UUID每次重试都调用 UUID.randomUUID() 会让系统把每次尝试视为新交易，造成重复发放或重复扣款。幂等重试取得原成功结果时状态仍为 SUCCESS，同时 replayed() 返回 true。

    信任边界与 API 边界

    Java 模组 API 的调用方与 Contribution 运行在同一个 JVM 中，属于服务器管理员主动安装的受信任代码。source 用于审计、统计、日志和可选的来源白名单，不作为无法伪造的安全身份凭证。API 仍会独立执行全部参数、数值和余额校验。

    其他模组不得：

    • 直接修改账户表或流水表；
    • 获取并长期持有数据库连接；
    • 绕过余额上下限或单次数量范围；
    • 自行计算变动前后余额；
    • 自行生成流水 ID；
    • 从客户端直接调用余额变更；
    • 把 IDEMPOTENCY_CONFLICT 当作普通网络错误重试。

    公共 API 遵循语义化版本：cn.contribution.api 中的类型在同一主版本内保持源代码与二进制兼容；删除类型、修改函数签名或改变既有状态语义时必须增加主版本。

    贡献系统命令

    打开界面、查询账户与流水、浏览账户列表的命令。

    1. 用途
    2. 本模块命令路径

    用途

    这一组命令是贡献值系统面向所有玩家的入口：打开图形界面、查询余额与流水、按游标翻页。除账户列表与全服流水外，普通玩家都可以使用自己的数据部分。

    • /contribution 打开首页；已安装客户端模组时使用专用界面，否则使用原版 Dialog。
    • /contribution leaderboard 打开排行榜，默认富豪榜，按当前贡献余额排序；其他榜在界面内切换。
    • /contribution diagnose 需要OP2或控制台权限，诊断并触发安全恢复，聊天栏反馈初始及复查报告。
    • /contribution ui <页面> 主要供界面按钮调用，也可以在聊天栏直接使用。
    • 账户列表与游标命令属于管理员工具，返回的游标由上一页提供，不需要手动构造。
    • 流水查询默认每页 20 条，单次最多 100 条；普通玩家只能查询最近 90 天的本人流水。
    ☀
    界面标识/contribution ui 接受 home、account self、history self、industries、checkin、admin、accounts、admin_search、back、previous、close 等页面标识，语义见界面与操作。

    账户管理命令

    增减余额、创建账户、迁移 UUID、清理假人账户与幂等重试。

    1. 用途
    2. 本模块命令路径

    用途

    这一组是管理员专用的经济操作入口。所有命令都在服务端的同一数据库事务内完成账户更新与流水写入，并遵守余额范围与幂等约束。

    • add / remove 的金额分别为 1—2147483647 与 1—2147483648；布尔参数决定是否同步影响历史总收入。
    • 目标支持玩家名称、UUID 或玩家选择器；选择器必须恰好选中一名玩家，多目标选择器会被拒绝。
    • 每次命令先返回请求 ID 与可点击的原请求重试文本，再异步执行。
    • retry 必须使用完全相同的目标、金额、原因、收入标志与备注，否则视为幂等冲突。
    • account migrate 只允许在主服务器控制台且没有在线玩家时执行，执行前必须备份。
    • bot_check 是破坏性清理，不会回滚已计入服务器建设度的历史汇总。
    ⚠
    不要把 retry 当作重复发放结果不明时使用 /contribution retry <原请求UUID> …，不要重新执行 add / remove，否则会生成新的幂等 ID 并可能重复变动余额。

    股票命令

    查看市场、买卖、批量交易、历史曲线与退市退款领取。

    1. 用途
    2. 本模块命令路径

    用途

    股票命令完全独立于 /contribution，使用 /stock 根命令。股票参数可以填写股票编号、中文名称、原版物品 ID 或其不带 minecraft: 的路径。

    • 交易只在每个游戏日 10:00—14:00 开放，对同一支股票每天最多买入一次、卖出一次。
    • 单次数量为 1—10000；买卖均收取 2% 手续费。
    • batch 逐只提交，最多 20 只，不是全批原子事务；编号以数值去重。
    • retry 与 batch-retry 必须保持原请求的参数与顺序，仅重试原交易，不会产生第二笔扣款。
    • claim 领取退市返还中因余额上限暂未入账的余款，退款不计入历史总收入。
    ✎
    主服时钟必须新鲜主服务器发布的观察时钟超过 5 秒未更新，或所属核算日尚未完成股价更新时，所有服务器都会暂停交易并明确提示。

    商店命令

    浏览与购买商品、刷新目录、领取待发物品与订单重试。

    1. 用途
    2. 本模块命令路径

    用途

    /shop 打开共享商品目录。原版客户端通过 26.3 原生 Dialog 浏览与购买，安装同一模组的客户端使用专用界面；两种界面共享同一个数据库目录与同一套校验。

    • 原版 Dialog 每页最多 8 件商品，可直接购买一份；购买更多使用 /shop buy <编号> <份数>。
    • 客户端界面会附带商品版本；目录过期时拒绝成交并提示刷新，不按玩家没看到的新价格扣款。
    • 文字命令省略版本时，以服务器当时的商品价格成交。
    • claim 领取商店与活动签到的待发物品；背包放不下的部分掉落在玩家附近。
    • 结果不明时使用 /shop retry <订单ID> <商品ID> <份数>，商品与份数不得改变。

    商店管理命令

    上架、下架、修改商品，以及完整管理表单的提交入口。

    1. 用途
    2. 本模块命令路径

    用途

    商店管理需要 OP 等级 2。/shop admin 打开图形管理界面；put_on、take_off、modify 提供文字入口，publish / save 是图形表单的提交命令。

    • put_on 自动分配稳定、不可复用的商品编号，排序默认 0。
    • modify 按名称、数量、售价、描述的顺序填写；只改后面的字段时前面填 -，未填写的尾部字段保持不变，描述填 "" 清空。
    • save 必须携带编辑页加载的实际 revision，其他管理员已经修改时拒绝覆盖。
    • 物品参数使用原版 ItemArgument，可以携带数据组件；完整定义最多 2048 字符。
    • take_off 只下架，不删除商品、历史订单或待发物品。
    • 目录最多保留 256 件商品（含已下架商品）。
